# Test Strategy

## 1. Objective

Цель тестирования — проверить корректность работы основных пользовательских сценариев, бизнес-логики и взаимодействия компонентов системы.

Основной фокус — критические сценарии, которые могут повлиять на данные пользователей, оформление заказов и доступ к функциональности.

## 2. Scope

В тестирование входят:

- регистрация и авторизация;
- управление пользователями;
- каталог товаров;
- поиск и фильтрация;
- карточка товара;
- корзина;
- оформление заказа;
- история заказов;
- административная функциональность;
- REST API;
- данные в базе данных.

## 3. Testing Types

### Functional Testing

Проверка соответствия реализованной функциональности требованиям.

### Regression Testing

Проверка того, что изменения не нарушили существующую функциональность.

### Integration Testing

Проверка взаимодействия frontend, backend, API и базы данных.

### API Testing

Проверка REST API, HTTP-кодов, структуры запросов и ответов, авторизации и обработки ошибок.

### Database Testing

Проверка корректности сохранения и изменения данных в базе.

### Exploratory Testing

Исследование системы без заранее определённого полного набора шагов для поиска неожиданных сценариев и проблем.

## 4. Test Design Techniques

Для подготовки тестов используются:

- классы эквивалентности;
- анализ граничных значений;
- позитивные и негативные сценарии;
- таблицы решений;
- проверка переходов состояний;
- pairwise testing при необходимости.

## 5. Priority

### Critical

Функции, отказ которых делает невозможным использование продукта или создаёт серьёзный риск для данных.

Примеры:

- авторизация;
- права доступа;
- оформление заказа;
- доступ к чужим данным.

### High

Важная функциональность, напрямую влияющая на основной пользовательский сценарий.

Примеры:

- корзина;
- поиск;
- изменение количества товаров.

### Medium

Функциональность, которая не блокирует основной сценарий.

### Low

Косметические и второстепенные проблемы.

## 6. Test Levels

Планируется проверять систему на нескольких уровнях:

UI → API → Database

UI используется для проверки пользовательских сценариев.

API — для проверки бизнес-логики и взаимодействия с backend.

Database — для проверки сохранности и корректности данных.

## 7. Regression Strategy

Перед релизом в первую очередь проверяются критические пользовательские сценарии:

1. Авторизация.
2. Просмотр каталога.
3. Добавление товара в корзину.
4. Изменение корзины.
5. Оформление заказа.
6. Просмотр заказа.

После этого выполняется расширенная регрессионная проверка.

## 8. Automation Strategy

Автоматизации в первую очередь подлежат:

- стабильные проверки;
- часто повторяющиеся сценарии;
- критические API-сценарии;
- позитивные и негативные проверки API;
- проверки, которые удобно выполнять автоматически при каждом изменении кода.

Нецелесообразно автоматизировать нестабильные или одноразовые проверки, если стоимость поддержки автотеста выше его пользы.

## 9. Defect Management

Обнаруженные дефекты фиксируются в виде баг-репортов.

Каждый баг должен содержать:

- краткое описание;
- предусловия;
- шаги воспроизведения;
- ожидаемый результат;
- фактический результат;
- окружение;
- Severity;
- Priority;
- необходимые вложения.

После исправления выполняется re-testing.

Если исправление затрагивает связанную функциональность, выполняется regression testing.

## 10. Entry Criteria

Тестирование начинается, если:

- доступно тестовое окружение;
- функциональность доступна для проверки;
- требования достаточно определены;
- подготовлены необходимые тестовые данные.

## 11. Exit Criteria

Тестирование может быть завершено, если:

- выполнены запланированные проверки;
- критические дефекты исправлены или согласован их статус;
- критические пользовательские сценарии успешно пройдены;
- результаты тестирования зафиксированы.

## 12. Risks

Основные риски:

- неполные или неоднозначные требования;
- ошибки в расчёте стоимости;
- некорректное управление доступом;
- потеря или неконсистентность данных;
- регрессии после изменений;
- различия между поведением UI и API.
