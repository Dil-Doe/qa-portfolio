# Баг-репорты

> Примеры оформлены как демонстрация подхода к документированию дефектов. Они не заявляются как реальные дефекты конкретного продукта.

---

## BUG-001 — Итоговая стоимость корзины не пересчитывается после изменения количества товара

**Severity:** Major
**Priority:** High

**Предусловия:**

* Пользователь авторизован.
* В корзине находится один товар стоимостью 1 000 ₽.

**Шаги воспроизведения:**

1. Открыть корзину.
2. Увеличить количество товара с 1 до 2.
3. Проверить итоговую стоимость корзины.

**Ожидаемый результат:**

Количество товара изменяется на 2, итоговая стоимость составляет 2 000 ₽.

**Фактический результат:**

Количество товара изменяется, но итоговая стоимость остаётся 1 000 ₽.

**Окружение:**

Web, desktop browser.

**Тип дефекта:** Функциональный / бизнес-логика

## BUG-002 — Пользователь без административных прав получает доступ к административному разделу

**Severity:** Critical
**Priority:** Critical

**Предусловия:**

Пользователь авторизован и не имеет административных прав.

**Шаги воспроизведения:**

1. Авторизоваться под обычным пользователем.
2. Перейти напрямую по адресу административного раздела.
3. Проверить результат.

**Ожидаемый результат:**

Доступ к административному разделу запрещён.

**Фактический результат:**

Административный раздел открывается.

**Окружение:**

Web, desktop browser.

**Тип дефекта:** Безопасность / авторизация

**Риск:**

Пользователь без необходимых прав может получить доступ к функциям, предназначенным для администратора.

## BUG-003 — Система позволяет создать заказ с нулевым количеством товара

**Severity:** Major
**Priority:** High

**Предусловия:**

Пользователь авторизован. В корзине находится товар.

**Шаги воспроизведения:**

1. Открыть корзину.
2. Установить количество товара равным 0.
3. Перейти к оформлению заказа.
4. Подтвердить заказ.

**Ожидаемый результат:**

Система не позволяет оформить заказ с нулевым количеством товара.

**Фактический результат:**

Заказ создаётся.

**Окружение:**

Web.

**Тип дефекта:** Валидация / бизнес-логика

## BUG-004 — Пользователь может получить данные заказа другого пользователя через API

**Severity:** Critical
**Priority:** Critical

**Предусловия:**

* Существуют два пользователя.
* У пользователя B есть заказ.
* Пользователь A авторизован.

**Шаги воспроизведения:**

1. Авторизоваться под пользователем A.
2. Получить идентификатор заказа пользователя B.
3. Отправить запрос на получение заказа пользователя B.
4. Проверить ответ API.

**Ожидаемый результат:**

API запрещает пользователю A получать данные заказа пользователя B.

**Фактический результат:**

API возвращает данные чужого заказа.

**Окружение:**

REST API.

**Тип дефекта:** Безопасность / контроль доступа

**Риск:**

Раскрытие персональных и коммерческих данных пользователей.

## BUG-005 — После изменения цены товара в административной части отображается старая цена

**Severity:** Major
**Priority:** High

**Предусловия:**

Товар существует в каталоге.

**Шаги воспроизведения:**

1. Открыть административную часть.
2. Изменить цену товара.
3. Сохранить изменения.
4. Открыть каталог.
5. Найти изменённый товар.
6. Сравнить отображаемую цену с новой ценой.

**Ожидаемый результат:**

В каталоге отображается актуальная цена товара.

**Фактический результат:**

В каталоге отображается предыдущая цена.

**Окружение:**

Web.

**Тип дефекта:** Функциональный / согласованность данных

## BUG-006 — Повторная отправка формы создаёт несколько одинаковых заказов

**Severity:** Major
**Priority:** High

**Предусловия:**

Пользователь авторизован и имеет товары в корзине.

**Шаги воспроизведения:**

1. Перейти к оформлению заказа.
2. Заполнить обязательные поля.
3. Несколько раз быстро нажать кнопку подтверждения заказа.
4. Открыть историю заказов.

**Ожидаемый результат:**

Создаётся только один заказ.

**Фактический результат:**

Создаются несколько одинаковых заказов.

**Окружение:**

Web.

**Тип дефекта:** Функциональный / бизнес-логика

**Риск:**

Пользователь может случайно создать несколько заказов вместо одного.
