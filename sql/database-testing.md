# Database Testing

## 1. Цель

SQL используется для проверки корректности данных, которые создаются и изменяются в результате действий пользователя через UI и API.

Основная задача — убедиться, что данные корректно сохраняются в базе, связи между сущностями не нарушаются, а информация в API соответствует данным в БД.

---


## 3. Проверка заказа пользователя

Получить все заказы конкретного пользователя:

```sql
SELECT
    o.id,
    o.status,
    o.total_price,
    o.created_at
FROM orders o
JOIN users u ON u.id = o.user_id
WHERE u.email = 'user@example.com';
```

### Что проверяется

* заказ действительно принадлежит нужному пользователю;
* идентификатор заказа корректный;
* статус сохранён;
* итоговая стоимость соответствует данным заказа.

---

## 4. Проверка состава заказа

Получить товары, входящие в конкретный заказ:

```sql
SELECT
    oi.order_id,
    p.name,
    oi.quantity,
    oi.price
FROM order_items oi
JOIN products p ON p.id = oi.product_id
WHERE oi.order_id = 1001;
```

### Что проверяется

* все товары заказа существуют;
* корректно установлена связь между заказом и товарами;
* количество товара соответствует заказу;
* цена сохранена корректно.

---

## 5. Проверка расчёта стоимости

Можно проверить, соответствует ли итоговая стоимость заказа сумме позиций.

```sql
SELECT
    o.id AS order_id,
    o.total_price,
    SUM(oi.quantity * oi.price) AS calculated_total
FROM orders o
JOIN order_items oi ON oi.order_id = o.id
GROUP BY o.id, o.total_price;
```

После выполнения сравниваются:

* `total_price`;
* `calculated_total`.

Если значения отличаются, необходимо проверить бизнес-логику расчёта стоимости.

---

## 6. Поиск дублирующихся email

Если email пользователя должен быть уникальным:

```sql
SELECT
    email,
    COUNT(*) AS count
FROM users
GROUP BY email
HAVING COUNT(*) > 1;
```

Ожидаемый результат — отсутствие записей.

Наличие результата требует дополнительного анализа и может указывать на нарушение ограничения уникальности.

---

## 7. Поиск заказов без существующего пользователя

```sql
SELECT
    o.id,
    o.user_id
FROM orders o
LEFT JOIN users u ON u.id = o.user_id
WHERE u.id IS NULL;
```

Запрос помогает обнаружить заказы, для которых отсутствует соответствующий пользователь.

При наличии таких записей необходимо проверить допустимость подобного состояния согласно бизнес-правилам.

---

## 8. Проверка данных после API-запроса

Например, пользователь создаёт заказ через API:

```text
POST /orders
```

API возвращает:

```json
{
  "orderId": 1542,
  "totalPrice": 3490
}
```

После этого можно проверить данные в БД:

```sql
SELECT
    id,
    user_id,
    total_price,
    status
FROM orders
WHERE id = 1542;
```

Полученные данные сравниваются с API-ответом.

Проверяется:

* идентификатор заказа;
* пользователь;
* итоговая стоимость;
* статус.

---

## 9. Проверка целостности связей

Для проверки связанных данных используются JOIN-запросы.

Например:

```sql
SELECT
    o.id AS order_id,
    u.email,
    p.name AS product_name,
    oi.quantity
FROM orders o
JOIN users u ON u.id = o.user_id
JOIN order_items oi ON oi.order_id = o.id
JOIN products p ON p.id = oi.product_id
WHERE o.id = 1001;
```

Так можно проверить всю цепочку:

```text
Пользователь
     ↓
Заказ
     ↓
Позиция заказа
     ↓
Товар
```

---

## 10. Подход к Database Testing

При проверке базы данных я обращаю внимание на:

* корректность сохранения данных;
* связи между сущностями;
* отсутствие неожиданных дублей;
* соответствие данных API и БД;
* корректность расчётов;
* наличие обязательных данных;
* целостность связанных записей.

SQL рассматривается не как отдельный навык, а как инструмент для проверки корректности работы приложения.
